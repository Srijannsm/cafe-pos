# QA report — Aaramva POS (26 Nov 2026)

## How it was tested
- **API security audit:** every controller and route checked for auth guard, role and cafe scoping.
- **90 end-to-end tests** (new, `apps/api/test/e2e`): the real API against a real PostgreSQL built from
  all 22 migrations, driven over HTTP. They include concurrency tests that fire simultaneous requests.
- **57 unit tests** (existing plus updated): all pass.
- **Fresh-database migration run:** all migrations apply cleanly to an empty database (a first production deploy).
- **Seed script** run on a fresh database: works.
- **Web:** typecheck, ESLint (actually linting TS/TSX now, 0 warnings), production build (34 routes),
  and a browser pass against the real API: 25 pages with no JS errors, console errors or failed API calls,
  plus the full waiter → kitchen → serve → bill → split payment → receipt flow through the UI.

## Bugs found and fixed

| # | Severity | Bug | Fix |
|---|---|---|---|
| 1 | Critical | Simultaneous payments on one bill all succeeded (3 taps on a Rs 180 bill recorded Rs 540) | Order row locked during payment; amount left re-checked inside the transaction |
| 2 | High | Deactivated staff kept working for up to 12 h on their existing login | Every request re-checks that the user and cafe are active; role read from the DB |
| 3 | High | Deactivating a cafe from /platform didn't log its staff out | Same as #2 |
| 4 | High | Logo upload saved the file with the uploaded name's extension: `x.html` or `.svg` would be served from the API | Only PNG/JPEG/WebP, verified by file signature; extension chosen by the server |
| 5 | High | Query numbers arrived as strings (`take + 1` = "301"), breaking "Load more" on Bills and report filters on the production engine | `ValidationPipe({ transform: true })` |
| 6 | Medium | Quick double "Generate bill" taps skipped bill numbers (gaps in a tax sequence) | served → billed claimed atomically before a number is taken |
| 7 | Medium | Two waiters opening the same free table at once created two orders | Table row locked; active-order check inside the transaction |
| 8 | Medium | Two "open shift" taps could open two cash drawers | Per-cafe lock |
| 9 | Medium | The last admin could deactivate or demote themselves (cafe locked out of admin) | Refused while no other active admin exists |
| 10 | Medium | Staff limit counted deactivated staff, so you couldn't replace someone who left | Counts active staff only; reactivation re-checks the limit |
| 11 | Medium | PIN `abcd` accepted, but the login keypad is digits-only (unusable account) | PIN must be 4 digits |
| 12 | Medium | Menu image upload trusted the browser's file type | Signature check (shared with #4) |
| 13 | Medium | `npm run lint` linted no TS/TSX at all (and the Babel parser couldn't parse TSX) | Shared config switched to typescript-eslint; real findings fixed |
| 14 | Medium | `NEXT_PUBLIC_API_URL` not declared in turbo.json, so a cached build could point at the old API | Declared |
| 15 | Low | Kitchen screen showed "TT5" for table "T5" (also the Bills page, dashboard and game) | `tableLabel()` helper |
| 16 | Low | No `.env.example`, weak or missing secrets not detected | `.env.example` for both apps; API refuses weak production config |
| 17 | Low | No security headers; `X-Powered-By` exposed | nosniff, frame-deny, referrer-policy; header removed |
| 18 | Low | Customer uploads committed to git | `/public/uploads/` ignored (see deploy checklist to untrack) |

## Verified working (no change needed)
Tenant isolation (cafe A can't read or change cafe B anything), role permissions, PIN lockout, QR ordering
(server prices, staff confirmation, rate limit, regenerated QR kills the old link, plan gating),
VAT on top and VAT-inclusive maths, discounts and caps, voids and cancels with audit log, tracked-stock
oversell protection, recipe deduction, purchases with weighted average cost, stock counts, cash-drawer maths,
plan feature toggles taking effect live, overdue cafes blocked, platform onboarding and PIN reset,
every report endpoint with filters.

## Open items (decisions or later work, not blockers)
1. **Trials never end automatically.** A cafe on trial keeps Premium until someone changes it on /platform.
   Decide: auto-move to the cafe's own plan, or to "overdue", after 14 days?
2. **The demo cafe from the seed** has known PINs: deactivate it in production (see the checklist).
3. **Single API process only** (in-memory lockouts, plan cache, game state). Fine for launch; needs Redis to scale out.
4. An already-open **socket** isn't dropped when a user is deactivated. Their data calls are refused, but
   live kitchen pushes continue until they reload. Low risk.
5. A QR order is added item by item. If one item sells out mid-submit, the earlier items stay on the order
   and the customer sees an error for the rest.
6. Not yet tested on real devices: iPhone Safari, Android Chrome, the thermal printer. Do the manual pass in the checklist.
7. Four noisy React lint rules are switched off with reasons in `packages/eslint-config/next.js`.
